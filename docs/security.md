# Модель безопасности

## Эксплуатация и границы доверия

MVP предназначен для локального использования в контролируемом окружении.
API не реализует аутентификацию и авторизацию. Любой процесс, имеющий к нему
доступ, может читать сохранённые события и отправлять новые.
Loopback ограничивает сетевой маршрут, но не удостоверяет клиента.
Прямое размещение в интернете или недоверенной многопользовательской среде
выходит за модель эксплуатации.

`source`, `host`, `timestamp` и `data` поступают от клиента. Они проходят проверку
формата. Их подлинность не подтверждается.
Недоверенные файлы проходят через SSH-, XML- и PCAP-парсеры.
YAML-правила, параметры БД и конфигурация запуска считаются входом оператора.
Доступ к ним позволяет изменить результаты анализа или направление записи.

Основные активы — события, корректность алертов и связей, доступность анализа,
учётные данные БД, правила и содержимое томов. Словарь `data` может содержать
чувствительные сведения. GET возвращает сохранённые поля без разграничения
по пользователям. На практике круг клиентов API должен быть ограничен настройками окружения.

## Проверки входа

Промежуточный обработчик ASGI считает фактически полученные байты POST-тела до JSON-разбора.
Лимит `SDE_MAX_REQUEST_BODY_BYTES` по умолчанию равен 5 MiB.
Учитываются chunked-тела без Content-Length. При превышении возвращается 413
до вызова Pipeline и записи. Сжатые тела отклоняются с 415.
REST-партия содержит не более 1000 событий.

Pydantic требует `timestamp` с часовым поясом, корректные enum и непустой
event_type. В проверяемых структурах допускается до 64 контейнеров с учётом
корневого. Циклы и неконечные float/Decimal в значениях и ключах словарей
отклоняются. JSON-сериализация `SecurityEvent` повторно проверяет data после
мутации. JSON-ключи HTTP-тела являются строками, проверки нестандартных
ключей важны для прямого Python API.

SSH проверяет адрес, порт, PID и время. Windows отклоняет конфликтующие
и повторные именованные EventData, отделяет неподдерживаемый Event ID.
PCAP использует транспорт выбранного внешнего IPv4-заголовка.
Повреждённые записи учитываются в статистике, когда формат позволяет
безопасно читать следующие записи. Структурно повреждённый XML или ошибка
чтения PCAP может завершить анализ исключением.
Предел HTTP-тела не применяется к файловому Python API.

Правила читаются через `yaml.safe_load` и проверяются моделями. Операторы заданы
перечислением, пути с точками обращаются к вложенным полям. Идентификаторы
`rule_id` внутри набора уникальны. Загрузчик не ограничивает размер и глубину
файлов правил YAML или сложность ссылок на повторно используемые узлы.

Ответы API на ошибки БД скрывают SQL, параметры подключения и трассировки.
Ответ 422 исключает полное входное значение. Серверные журналы требуют
контроля доступа, особенно при нестандартной конфигурации диагностики.

## Целостность и права БД

Одна HTTP-партия сохраняется транзакционно. Commit предшествует успешному
ответу. Ошибка вызывает rollback событий и связанных алертов.
PK запрещают повтор UUID, внешние ключи требуют существующих событий.
Уникальность (correlation_id, `event_id`) запрещает повтор события в одной
корреляции, position сохраняет порядок.

На реальной PostgreSQL проверены независимые Session, конкурентная запись,
один успех и один 409 при одинаковом UUID, отсутствие частичной партии
проигравшего запроса, невидимость незавершённой записи и работоспособность
после rollback. UUID не доказывает подлинность события и не предотвращает
повторную отправку одинакового содержания с новыми UUID.

Роль `sde_migrator` владеет объектами схемы
и применяет миграции. Роль `sde_runtime` получает SELECT/INSERT данных приложения
и SELECT alembic_version. Ей запрещены DDL, UPDATE, DELETE, TRUNCATE и TEMP,
административные атрибуты и членство в других ролях.
Привилегии по умолчанию распространяют SELECT/INSERT на будущие таблицы мигратора
в public. Дополнительные объекты требуют отдельного определения прав.
Назначение ролей и переход существующего тома описаны в
[deployment.md](deployment.md).

Readiness подтверждает соединение, ожидаемую ревизию и наличие четырёх таблиц.
Она не сравнивает все столбцы и индексы. Для сопоставления схемы используется
alembic check.

## Контейнеры и секреты

API работает с UID 10001 и корневой файловой системой только для чтения.
Для контейнера заданы `cap_drop: [ALL]`, `no-new-privileges` и ограниченный по размеру
`tmpfs` в `/tmp`. Порт API привязан к `127.0.0.1`. Порт БД доступен внутри сети
`backend`. API также подключён к сети `frontend`, через которую возможны исходящие соединения.

Администратор, мигратор и приложение используют разные пароли.
API получает только пароль `sde_runtime` через `PGPASSWORD`.
БД при инициализации получает все три пароля для создания ролей.
Администратор Docker может читать окружение контейнеров и содержимое томов.
Непривилегированный UID и настройки контейнера уменьшают доступные полномочия,
но безопасность также зависит от хоста и Docker Engine.

.gitignore исключает env-файлы и pgpass, .dockerignore исключает секреты,
локальные окружения, кеши, IDE и служебные каталоги из контекста.
Dockerfile копирует выбранные пути проекта. Проверяйте, что секреты не попали
в src или migrations. Удаление файла последующим RUN не удаляет его из
раннего слоя образа. Правила исключения не действуют на данные, уже попавшие в историю Git.

## Выполненные проверки

Проведена ручная проверка архитектуры и безопасности кода.
После исправлений выполнены регрессионные тесты с PostgreSQL,
проверки привилегий, Docker-конфигурации, ограничений HTTP и восстановления БД.
Результаты интеграционных проверок и измерений приведены в
[development.md](development.md).

26 ноября 2026 года проверены 25 пакетов, установленных для работы приложения в Linux-образе.
Версии совпали с `constraints-runtime.txt`, pip check не обнаружил нарушений.
Pip-audit 2.10.1 выполнен в отдельном временном контейнере, в образ приложения он
не устанавливался. Инструмент не сообщил об известных уязвимостях проверенных
пакетов. Временный контейнер завершился с --rm и был удалён, временный образ
инструмента сохранялся. Названия и версии публичных пакетов передавались
сервису проверки с разрешения владельца. Использован сервис PyPI,
выбираемый по умолчанию pip-audit 2.10.1. Параметр выбора сервиса в команде
аудита не задавался. Это подтверждено справкой той же версии инструмента.

Ограниченный локальный шаблонный поиск охватил 11 коммитов и 142 уникальных
объекта Git с содержимым файлов. Совпадения в URL и присваиваниях оказались
примерами значений и ссылками на переменные. Шаблоны не выявили реальных секретов.
Проверка ограничивалась доступной историей и известными шаблонами учётных данных.

Полный аудит системных пакетов Docker-образа и проверка ядра хоста не выполнялись.
Проверки зависимостей отражают известную базу уязвимостей на дату запуска.

## Остаточные риски

В настройках проекта нет совокупного бюджета памяти и CPU для всех
конкурентных запросов, ограничения частоты запросов, квоты диска или автоматического удаления
старых событий. Несколько допустимых запросов могут совместно исчерпать ресурсы.
Файловые анализаторы собирают результат в память, отдельные большие элементы
XML и файлы правил YAML также требуют ресурсов.

Корреляция ограничена одной партией и одним жадно выбранным кандидатом на
группу. Отсутствие алерта не доказывает отсутствие подходящей последовательности.
Разрешённые форматы входа и протоколы перечислены в [usage.md](usage.md).

Исходный IP клиента и содержимое события не являются механизмом авторизации.
Роли БД защищают границу процесса и хранилища, но процесс API всё ещё
может читать все события и добавлять новые.
Сохранность данных зависит от резервного копирования, защиты env-файла,
доступа к средствам управления Docker и конфигурации среды.
